# 当前玻璃效果的性能成本（2026-09-22）

后续按“显示效果完全不变”的约束实施了导航查询缓存优化，见
[优化验证记录](glass-optimization-2026-09-22.md)。下列数据属于此前的成本评估，
不是后续优化的收益；后续未采用视觉降级或简化边框模式。

当前完整玻璃有明显滚动成本，不能称为廉价装饰。桌面样本中平均帧间隔
从关闭玻璃时约 16.7ms 增加到约 25ms。仅关闭玻璃边框和附加内阴影后，
两个页面均回到约 16.7ms。基础毛玻璃仍消耗额外主线程时间，但在这次环境中
没有让帧间隔明显超过 60Hz 的预算。

## 测试条件与范围

- 当前提交：`8a6899b`，包含两个课程 Accordion 的局部禁用图层提升修复。
- 隔离 Next.js 生产构建，业务源码未修改；测试开关只存在于临时副本。
- Chrome 153.0.8010.48，headless，Intel i7-1360P / Iris Xe，GPU 加速。
- 桌面 1440×900 / DPR 1；手机尺寸 390×844 / DPR 2。
- 暗色图片背景；18 个虚构课程、12 张虚构单词卡；API 全部使用测试响应。
- 三种模式：完整玻璃；保留基础毛玻璃但隐藏 `.glass-border` 与 `.yyk`；
  隐藏毛玻璃、玻璃边框及 `.yyk`，并跳过导航源滤镜。
- 关闭模式保留普通阴影、页面壁纸、透明底色、布局和业务内容。它不是一个
  完整的纯色主题，也不是从依赖图中彻底删除所有玻璃代码的版本。
- 三种模式都保留共享壁纸缓存及表面控制器。关闭边框模式不注册边框层。
  因此这里衡量预热后的滚动成本，不量化取消缓存的启动时间或内存收益。
- 每个页面/尺寸/模式执行两次，顺序为 full/base/plain、plain/base/full；
  共 24 个有效样本。每次先等待缓存与图表稳定，再预热并执行四段同速滚动，
  每段约 2 秒。截图、编码、主题切换不在计时区间内。
- 课程页展开自建分类后滚动 1400px；桌面单词页高度较短，滚动 359px；
  手机尺寸单词页滚动 1400px。页面间绝对耗时不能直接作为组件数量的比例。
- 模式及可见装饰层数量均有记录，最终样本没有页面异常。早期脚本错误及
  未完成的运行已弃用。

## 实测结果

以下先计算每次的指标，再取两次平均。帧间隔来自 `requestAnimationFrame`，
不是直接测得的 GPU 呈现 FPS。两次样本只能说明这台机器的现象，不能给出
所有设备通用的下降百分比。

| 页面/尺寸 | 完整玻璃帧间隔 | 无玻璃边框帧间隔 | 关闭玻璃帧间隔 |
| --- | ---: | ---: | ---: |
| 课程页，桌面 | 25.29ms | 16.67ms | 16.70ms |
| 单词页，桌面 | 24.87ms | 16.72ms | 16.68ms |
| 课程页，手机尺寸模拟 | 16.68ms | 16.68ms | 16.73ms |
| 单词页，手机尺寸模拟 | 16.67ms | 16.70ms | 16.67ms |

桌面完整玻璃相对关闭状态，平均帧间隔增加约 49%–51%。这是帧间隔增加，
不是“FPS 下降 50%”；若仅按间隔倒数理解，对应节奏约由 60 次/秒降到
40 次/秒，即约三分之一。完整玻璃桌面样本超过 25ms 的帧约为 46%–49%，
关闭后约为 0.3%。鼠标滚动中确实存在可感知的不均匀帧节奏风险。

| 页面/尺寸 | 完整玻璃主线程任务时间 | 无玻璃边框 | 关闭玻璃 |
| --- | ---: | ---: | ---: |
| 课程页，桌面 | 1879ms | 1269ms | 300ms |
| 单词页，桌面 | 1289ms | 1152ms | 269ms |
| 课程页，手机尺寸模拟 | 1673ms | 1257ms | 316ms |
| 单词页，手机尺寸模拟 | 1868ms | 1121ms | 326ms |

这些是每次约 8–9 秒滚动内的 renderer 主线程任务总时间，不是整机 CPU 使用率。
完整效果约为关闭效果的 4.8–6.3 倍；两种手机尺寸样本约为 5.3–5.7 倍。
基础毛玻璃保留了明显的额外开销，即使画面仍跟得上刷新率。
没有超过 50ms 的主线程长任务，并不代表合成、光栅或呈现没有掉帧。

移除边框和附加内阴影使桌面帧间隔恢复到约 16.7ms，是强烈的成本来源线索。
这次没有把饱和细边、两级遮罩、20px 内发光和 `.yyk` 内阴影分别消融，
不能把所有成本都精确归于其中某个 CSS 属性。

## 为什么有成本

基础毛玻璃不是每张卡片每帧实时 `backdrop-filter`：`glass-wallpaper-cache`
提前生成共享的 base/border 两张图片，缓存命中时 CSS 为 `filter: none`。
这是有效优化，但固定背景、圆角裁剪、透明混合、多个图层仍需浏览器绘制。

玻璃边框比普通 1px border 复杂：饱和边框图、方向高光、内发光分别叠加，
内发光包含角度与深度两层 mask。当前配置四边内发光宽度均为 20px。
导航还会对穿过顶部的内容施加 SVG 局部源滤镜，滚动时更新其几何位置。
弹窗打开时则使用另一套整页源滤镜；此次未做弹窗开启/动画的单独计时。

页面静止、动画结束后没有永久主动重绘循环；主要持续成本发生在滚动、
布局变化、动画期间。首次加载、未缓存主题切换、窗口尺寸变化还会生成、
编码和解码纹理，可能产生短时工作峰值。

## 移动设备与内存

手机尺寸模拟依然运行在桌面 CPU/GPU 上，不能代替 Android/iPhone 真机。
测试没有温度、耗电、持续运行降频数据，不能声称一定发热，也不能保证不发热。
持续滚动期间的额外图形与 CPU 工作确实会增加功耗风险；低端 GPU、高 DPR、
高刷新率和热降频后的设备更容易掉帧。

按 4 字节 RGBA 像素估算，仅两张视口纹理：

| 视口 | 当前 base+border | 两组主题/尺寸缓存最多四张 |
| --- | ---: | ---: |
| 1440×900 / DPR 1 | 约 9.9MiB | 约 19.8MiB |
| 390×844 / DPR 2 | 约 10.0MiB | 约 20.1MiB |
| 390×844 / DPR 3 | 约 22.6MiB | 约 45.2MiB |

这不是实际显存读数，也不包含生成中的 Canvas、源图片解码、滤镜中间面及
浏览器合成层；资源共享和驱逐策略由浏览器决定。DPR 从 2 升到 3，像素数
增加 2.25 倍。压缩 JPEG 文件很小，不等于解码后的图片或 GPU 纹理也很小。

## 建议

优先为移动设备/低性能设备提供真正的简化边框模式：关闭内发光、复杂遮罩和
附加内阴影，以普通细边框替代，同时允许保留基础毛玻璃。现有“玻璃加强”
开关只是把部分强度/宽度归零，仍保留边框图、DOM、mask 和纹理，不等同于
本次完全隐藏玻璃边框的对照，也不能直接承诺获得本次同等收益。

还需要真机连续滚动、主题切换及弹窗测试，才能量化温度、功耗和长时间卡顿。
本轮只做评估，没有改变项目视觉效果或添加降级开关。
