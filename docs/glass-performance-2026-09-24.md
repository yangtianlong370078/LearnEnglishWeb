三种显示模式性能分析（2026-09-24）

本报告针对当前生产构建：卡片和玻璃模糊半径为 8px，液态玻璃为 4px；主题和模式在 head 中恢复；内容不等待液态初始化；另一种模糊半径在当前缓存发布后由 Worker 预生成。报告不改动应用行为。

完成 45 次正式采样（15 种场景，每种 3 次）、4 次补充诊断，以及 40 轮液态切换与 20 轮普通模式对照。最明确的差异在持续滚动：液态增加主线程工作，PC 单词页尤其明显；卡片和玻璃的差距较小，不能保证每个场景都严格按卡片、玻璃、液态排列。单纯移动鼠标和充分静止时，三者差距很小。

当前方案适合保留为日常可选的视觉模式，但尚不足以保证不同设备、不同页面都能持续流畅。取消首屏展示门槛、缓存复用和后台预生成有效地减少了等待来源；它们没有消除折射绘制、画布复制和图片内存成本。循环测试还发现了两种切换路径共有的节点/监听器累积信号，需要排查保留链后再评价长期稳定性。下文评级区分实际测量与工程判断。

**测量条件与指标含义**

- Windows 11，i7-1360P（12 核、16 线程）、约 32 GiB 内存、Intel Iris Xe；Chrome 153.0.8010.53，无头运行，ANGLE D3D11 硬件加速开启。
- 独立生产服务器 `127.0.0.1:8094`；深色照片背景；`/courselearn` 使用 12 张虚构单词卡，`/learnwords` 使用 18 个虚构课程，滚动前展开分类。所有接口均为固定模拟数据。
- PC：1440×900、DPR 1。移动模拟：390×844、DPR 2、触屏和粗指针。另加移动布局 + 4 倍 CPU 限速压力测试。它们仍使用电脑的 CPU/GPU，不能代替安卓或 iPhone 真机结果。
- PC 和移动模拟对两个页面、三种模式各执行 3 轮；CPU×4 压力测试仅覆盖单词页。模式顺序轮换，只有一个测试页面运行。每轮包含首次进入、静止采样、上下滚动、PC 鼠标移动、同一上下文重新加载。
- PC 使用原生合成鼠标滚动；移动模拟使用 `touchStart/touchMove/touchEnd`，每方向约 2 秒、路径约为屏高的 60%，结束前停顿以抑制惯性。所有样本均验证实际页面位移。移动合成滚动 API 未造成位移的试跑被排除，未进入结果。滚动结果反映当前模式缓存和首次液态初始化完成后的交互，未覆盖进入后立即滚动的争用情况；两种设备的面积、DPR、滚动距离和效果预算不同，不能据此比较 PC 与真实手机孰快。
- 表格为各轮指标的中位数；括号内范围为 3 轮最小值–最大值。样本量较小，无法把十几毫秒差异视为稳定的模式优势。
- FCP 是浏览器首次内容绘制；“数据出现”是首次在 DOM 文本中发现测试内容，并不保证该内容已经显示在屏幕上；`.app-shell` 可见只是页面外壳存在，不能当作完整内容就绪。
- “背景就绪”是两张当前模糊图片解码并发布；“液态首次拷贝”是观察到折射画布拷贝提交，不等于 GPU 已呈现完整首帧。两者都不构成内容展示门槛。
- rAF/s 是主线程动画回调的投递频率，**不是屏幕实际呈现 FPS**。P95 是 95% 回调间隔不超过的时间，越低越好。>25ms 是长帧间隔比例；60Hz 下一个理想间隔约 16.7ms。不能把 rAF 统计直接称为浏览器掉帧率、INP 或触摸延迟。
- `taskMs` 是渲染器主线程任务耗时，不包括全部 Worker、GPU 或整机 CPU 开销；>50ms 长任务能发现明显主线程阻塞，但没有长任务也不能证明合成流畅。
- 拦截请求用于隔离真实数据，同时关闭了浏览器 HTTP 缓存。因此“重新加载”是同一上下文再次导航，**不是正常 HTTP 热缓存测试**；首次进入也没有清空操作系统/浏览器共享资源缓存。

所有三种模式都保留模糊图片、边框结构以及导航栏的源过滤；“卡片”主要关闭高光、内发光和内阴影，不是纯色无特效模式。因此卡片也可能滚动不够平稳，不能把所有卡顿归因于液态。

液态在滚动更新时读取可见卡片坐标、进行一次批量 WebGL 绘制，再向每张选中的卡片 Canvas 拷贝。一次 WebGL draw 并不代表整页只有一次工作；全矩形 tile 都运行片元着色器，中心透明也不等于只计算边缘。背景模糊图片被重复使用，并非每次滚动重新生成 4px/8px 图片。

**鼠标移动、静止、模式切换和改变窗口大小**

PC 两个页面、三种模式的鼠标移动测试，中位数均约 60rAF/s，P95 约 16.8–16.9ms；液态 draw/copy 增量均为 0。没有证据表明纯鼠标移动会持续驱动折射计算。

正式采样中，课程分类刚展开后的 1s“静止”仍有约 520–602ms 主线程任务，不能当作稳态闲置开销。补测等待页面充分稳定、运行中动画归零后，玻璃/液态两页在约 1.2s 内仅有 13–26ms 主线程任务，液态 draw/copy/upload 均为 0。采样探针自身持续运行 rAF，不能把这些数字直接换算为整机闲置 CPU 或耗电。

- 纯鼠标位移没有专门的液态重绘监听。鼠标经过引起 hover 颜色/阴影变化时，主要成本来自 CSS 绘制；若触发尺寸/布局动画，则可能暂停或重新绘制液态。本次轨迹不代表所有菜单、弹窗和编辑操作。
- 卡片和玻璃共用 8px 缓存，彼此切换可复用图片。8px 与 4px 两组已预热完成时，玻璃与液态切换可省掉模糊图片生成；但离开液态会销毁 WebGL，重新进入仍需要上下文、着色器与纹理初始化，不能承诺零成本。
- 若立刻切换且另一组仍在生成，会复用进行中的任务；若 Worker 不支持，则按需生成。内容仍可通过 CSS 回退显示，效果就绪可能稍晚。
- 窗口大小、DPR、主题或明暗变化会改变缓存键。resize 100ms 防抖后先生成当前模式，再后台预生成另一组；连续缩放可能产生额外临时分配和绘制，液态还要调整 atlas/画布。
- 预生成由 Worker 执行，减少主线程串行等待；CPU、GPU 和内存带宽仍共享。在弱设备上可能与交互争用，不能保证所有设备完全无感。后台 Worker 完成后释放，不会一直运行。

**内存、耗电与移动端边界**

图片背景下，目前连卡片模式也会预生成另一种半径。稳态最多保留两组、每组基础图+边框图，共四张生成图片。因此双半径缓存成本并非只在用户选择液态时才发生。

下面按 `宽×高×DPR²×4 字节×图片数` 给出 RGBA 像素量参考，**不是实测 RAM/显存，也不是严格的分配下限**。同样分辨率下，4px 和 8px 图片像素量相同；减少模糊半径不会把图片内存减半。

| 视口 | 一组、两张 | 两组、四张 | 多保留一组的增量 |
| --- | ---: | ---: | ---: |
| 1440×900，DPR 1 | 9.89 MiB | 19.78 MiB | 9.89 MiB |
| 390×844，DPR 2 | 10.05 MiB | 20.09 MiB | 10.05 MiB |
| 390×844，DPR 3 | 22.60 MiB | 45.20 MiB | 22.60 MiB |

以上不含原图解码、压缩 Blob、临时 Canvas/ImageBitmap、合成器和 GPU 副本。深色原图 4368×2448 的 RGBA 像素量约 40.79 MiB；原图在两种半径间共享。液态还增加背景纹理、atlas、逐卡片画布；JS heap 统计不会涵盖这些成本，不能以 JS heap 更低断言液态更省内存。

液态 PC 预算为最多 20 张卡片、atlas DPR≤1、150 万像素；移动为最多 15 张、atlas DPR≤1、50 万像素，移动关闭色散，着色器从三次纹理采样减为一次。`maxPixels` 分别作用于背景与 atlas，不是全部显存上限；**共享模糊背景缓存依然使用真实 DPR**。旧前台生成任务未主动中止，连续 resize 时峰值可能高于稳态四图的像素量。

连续 8 次滚动更新均满足“工作耗时 >8ms，或 34ms<更新间隔<250ms”，才会临时清除折射，停止滚动 160ms 后恢复。此时仍是 liquid 模式和 4px 底层，只有 WebGL 不可用等永久失败才转为普通 glass。34ms 阈值不能保证 60Hz 始终稳定，更不能保证 90/120Hz。

静止不持续绘制，有利于减少液态的持续开销；滚动时增加的纹理采样、画布拷贝和内存带宽通常意味着更高能耗风险。本次没有电池功耗、温度或长时间热降频测量，不给出耗电百分比。移动模拟在 PC 上更快也不代表手机更快，真实 GPU、Safari 合成、内存压力、地址栏变化和散热均不同。

**使用与后续优化判断**

普通 PC 日常阅读、低频滚动可以选择液态，优先视觉效果的用户有理由保留它；频繁滚动单词列表、同时运行重应用、使用高分辨率屏幕时，玻璃或卡片更稳妥。移动端已有减配，模拟结果良好，但应在目标手机上验证后决定是否常开；低端设备和续航优先场景建议先用卡片或玻璃。

“两组模糊缓存已预热”能减少模式切换时重新生成背景的等待，但不能推出“液态与玻璃只有缓存成本差异”。日常使用的主要额外成本在滚动绘制；长时间静态阅读则小得多。

综合工程评价为 **B−：可日常使用的可选视觉模式，密集滚动仍有明显短板**。这是基于当前实现和本次测量的定性评价，不是跨设备基准评分。评级口径：A 表示目标场景表现稳定且有余量，B 表示日常可用但有取舍，C 表示已观察到影响连续性的性能问题，未验证项目不打分。

| 维度 | 评级 | 依据与边界 |
| --- | --- | --- |
| 内容优先展示与启动设计 | B+ | 首屏不等缓存/折射，模式提前恢复，另一组后台准备；冷进入仍有初始化长任务，慢 CPU 下背景要约 3s |
| PC 密集单词卡滚动 | C | 液态 36.4rAF/s、P95 50ms、长任务中位 7 个；相对玻璃主线程工作约翻倍 |
| PC 课程列表滚动 | B− | 液态约 51rAF/s，存在长间隔；测试路径只有部分区间显示折射，不能外推到全屏密集液态卡片 |
| 鼠标移动与静态阅读 | A− | 两页均约 60rAF/s，稳定时没有液态持续 draw/copy；没有测所有交互或电池功耗 |
| 移动布局模拟 | B+（仅模拟） | 普通模拟约 60rAF/s、无降级；CPU×4 液态约 53rAF/s；真机 GPU、温度与续航尚未评级 |
| 内存效率 | C+ | 缓存有数量上限，液态有像素预算；共享缓存无 DPR 上限，DPR 3 双组约 45MiB 像素量且另有原图/纹理 |
| 液态渲染资源管理 | B | 已有单 WebGL 上下文、批量绘制、静止停绘、可见性筛选和销毁；循环退出能释放画布/上下文；仍有共同 UI 资源累积待排查 |
| 数小时稳定性、手机热降频和耗电 | 暂不通过长期验证 | 短时切换出现节点/监听器累积信号；未定位引用链，也未覆盖数小时运行、Safari/安卓差异、温度与功耗 |

**短时反复使用检查**：在同一单词页通过实际模式选择 UI 执行 40 轮 `玻璃→液态→玻璃`（80 次切换），每轮加入短滚动，期间改变窗口尺寸，约 115 秒完成。再执行 20 轮 `玻璃→卡片→玻璃` 对照，约 58 秒完成。两组都先热身，在相同玻璃状态强制 GC 后采样；测试器自己保存的历史 WebGL 强引用在每轮退出检查后清除。

| 检查项 | 液态循环 40 轮 | 卡片对照 20 轮 |
| --- | ---: | ---: |
| GC 后 JS heap，热身→循环结束 | 7.86→10.13 MiB | 7.80→9.26 MiB |
| CDP DOM 节点数，热身→循环结束 | 1274→4234（+2960） | 1274→2754（+1480） |
| 事件监听器，热身→循环结束 | 631→1191（+560） | 631→911（+280） |
| 每轮退出后的液态画布 / 活跃 WebGL | 0 / 0 | 0 / 0 |
| 稳定检查点的缓存 Blob URL 数 | 4 | 4 |
| resize 过程中观测到的 Blob 峰值 | 6，随后回到 4 | 6，随后回到 4 |
| 后台 Worker / 页面异常 | Worker 均结束 / 0 异常 | Worker 均结束 / 0 异常 |

液态绘制资源的释放和缓存数量限制在这个范围内正常，未发现 WebGL 上下文越切越多。但两组都有每轮约 **+74 个 DOM 节点、+14 个监听器**的相同增长，且出现在 GC 后。CDP 节点计数可包含未释放的游离节点，不等于可见页面越来越长；这是共同 UI/切换测试路径的保留信号，尚未通过 heap snapshot 定位到具体组件、库或自动化保留链，不能直接断言为某个组件的生产内存泄漏，也不能忽略它而声称长期完全无累积。

这项结果对应“反复操作模式选择器”，不能外推为“静止开着液态也每秒泄漏”。频繁切换者应先排查该路径；只选定液态后阅读的用户，主要关注滚动和内存预算。数分钟检查不构成数小时稳定、无泄漏或省电证明。

优化空间仍然较大，建议按以下顺序推进。预期收益是根据路径和测量做出的判断，未实施前不承诺固定百分比。

| 优先级 | 优化方向 | 证据 / 预期收益 | 代价与验证重点 |
| --- | --- | --- | --- |
| P0 | 定位共同切换路径的节点/监听器保留 | 液态与卡片对照均每轮增加 74 节点、14 监听器；先用相同条件 heap snapshot 比较 detached nodes 和引用链，分离选择器打开/关闭与模式事件 | 尚不能指定泄漏责任组件；修复后重跑同一循环，观察 GC 后是否趋于稳定，不能只检查 WebGL 数量 |
| P0 | 自适应改用短窗口统计与分档画质 | 当前 PC 单词页约 36rAF/s 仍没有触发保护。滚动期间统计 300–500ms 窗口的超预算比例；逐步关闭色散、降低像素/卡数，最后才暂停折射 | 视觉会减弱；恢复需迟滞，避免反复闪切。不能仅把 34ms 硬改为 16.7ms，否则容易受抖动影响 |
| P1 | 减少逐卡片复制面积与次数 | 单词页约 4.3s 有 140 次批量 draw、1774 次 Canvas 拷贝。优先裁剪视口外部分，并按可见面积预算选择表面 | 保留原始卡片坐标/圆角用于着色，验证滚入滚出、圆角和重叠。不能仅靠减少 WebGL draw 数，因为现在已批量绘制 |
| P1 | 限制共享模糊缓存 DPR / 总像素 | 共享缓存使用真实 DPR；DPR 3→2 的像素量减少 55.6%，示例四图从 45.20 降至 20.09MiB | 这只是像素量降幅，不是总内存或耗时降幅。需对比细边框、渐变和背景清晰度，保持 cover 几何一致 |
| P1 | 当前模式的缓存生成也使用可抢占 Worker | 当前只有备用半径用 Worker；当前模式仍启动主线程 Canvas 路径。前台高优先级任务可抢占预热，过期 resize 任务尽早取消 | Worker 启动和传递也有成本，不保证总完成时间更短；保留兼容回退和内容优先显示 |
| P1 | 隔离分析共同导航栏过滤与页面绘制 | 普通卡片/玻璃在单词页也只有约 44/40rAF/s。滚动时测量顶层 host 并挂 SVG 源过滤，值得缩小候选集合、检查过滤承载面积 | 尚未通过开关对照证明它是主瓶颈。先做隔离测量，再改动，避免导航栏穿透和裁剪回归 |
| P2 | shader 对完全透明中心提前输出 | 当前透明中心仍执行后续法线/幂函数/纹理采样，可尝试跳过或采用边缘几何 | GPU 分支收益需实测；此项不减少 atlas 分配和逐卡片拷贝，不应把它当作全部瓶颈 |
| P2 | 让预热更有选择性 | 卡片也预热液态，可根据切换意图或空闲情况准备，减少未使用液态时的资源占用 | 首次突然切换可能更晚，是资源与切换速度的明确取舍，不优先于滚动优化 |
| P2 | 有期限地复用液态渲染器 | 可降低频繁比较模式时重建上下文与着色器的成本 | 非液态时会多保留资源；应短时保留并及时释放，不能无限常驻 |

为何 36rAF/s 仍没降级：其平均间隔约 27.8ms，小于 34ms；60Hz 下隔一帧的 33.3ms 也小于阈值。偶发 50ms 后下一次正常更新又清零连续计数。规则统计成功液态更新，CPU 提交时间也不能完整反映异步 GPU/合成压力。因此当前保护适合处理连续严重慢帧，不能把 `throttled=0` 当成流畅达标。

不建议第一步直接换成全页面单个显示 Canvas：它虽可能减少复制，却需要重新解决卡片、文字、菜单和弹窗的 DOM 层叠/裁剪关系，回归风险较大。也不建议先做无证据的逐行 JS 微优化；本次更有依据的方向是画布像素工作、共同过滤和预算控制。

下一轮验收可将“同一基准下 60Hz 目标的 P95 接近 16.7–20ms、>25ms 间隔比例明显下降、密集页面长任务减少，同时保留明确液态覆盖率”作为项目目标。再补 Android Chrome / iPhone Safari 真机持续滚动与阅读、90/120Hz、后台恢复、连续 resize、30–60 分钟使用和温度/内存趋势，才能提升长期与跨设备评级。

如果继续优化，优先检查共同的滚动合成/导航栏源过滤，以及液态逐卡片 Canvas 拷贝；如果希望卡片成为真正的低功耗模式，可另行考虑关闭它的非必需图片预热和装饰层。单纯把液态的 4px 改回 8px，在同一尺寸和主题下可以省去另一种半径的缓存，但不会消除液态滚动的 WebGL 和拷贝成本。
